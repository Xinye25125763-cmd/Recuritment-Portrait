# GiveMeOC 集成修正设计

## 复核结论

上一轮优先级成立，但原执行边界需要补上两点：历史意向岗位也必须能从意向快照恢复；GiveMeOC 的“岗位”字段是公司级职位列表，不是每个职位的 JD 职责。增强数据只能用于职位线索、公司、地点、批次、截止时间和投递入口，不得据此生成职责、关键词或经历缺口。

本轮仅在本地项目目录修复应用和数据生成脚本，不抓取网站、不覆盖已生成的增强库、不改动个人档案和投递记录。项目目录没有 Git 元数据，修改前后的回滚只能依靠文件级备份或用户已有副本；本轮只修改明确列出的文本代码和文档文件。

## 设计决策

### P0：统一岗位来源和诚实评分

- 新增共享岗位库模块：内置库必须成功加载，增强库可选加载；以岗位 ID 去重，增强库记录覆盖同 ID 的旧记录。
- 匹配、意向、简历页面统一使用该模块。
- 新增意向时保存必要岗位快照。解析历史意向时先查现有岗位库，再使用快照；旧意向没有快照时，使用其已有公司、标题、方向、地点和批次构造“元数据有限”的占位岗位，保留意向并禁止把它当完整 JD。
- 评分函数允许岗位数据维度返回不可用。只用可评维度按原始权重重新归一化，另返回数据覆盖率；缺失职责和关键词时不产出相关性、技能缺口或伪中性分。公司类别不明时不再默认互联网公司。
- 页面明确显示“依据有限”和覆盖率。等级含义仍表达匹配分数区间；资料完整度单独显示，避免把高分误读成高置信度。
- 无职责和关键词的公司级岗位线索不启动经历挖掘，不显示 0/0 进度；明示需要具体岗位 JD。无法提供链接时不输出空链接。

### P1：修正增强数据建模与生成器

- 逐个处理源表“岗位”列，以顿号、逗号、分号和换行作为安全分隔符；不按斜杠拆分。对每个片段单独推断受支持的方向，只为片段产出岗位记录。
- 记录保留原始片段、源公司类型、来源、投递入口及截止日期；标记内容类型为职位列表。不给它生成 responsibilities 或 keywords。公司、职位、方向、招聘批次、官方入口和截止日期均相同的记录去重并汇总地点；这些投递字段不同时保留为不同线索。ID 使用稳定字段哈希，不用运行顺序追加编号。
- 生成脚本支持命令行指定输入和输出；默认路径相对于脚本位置。站点抓取脚本的缓存、工作簿和补充信息路径也改为脚本目录下的默认值，并可指定路径。不会执行抓取。
- 简历经历文案只能使用用户提供的回答或经历事实。模板缺少变量时移除该主张或退化到不包含它的模板，不填入“显著提升”“核心指标”“相关团队”等虚构结果、规模或对象。
- UI 显示增强记录的投递截止日期和源公司类型；没有官方入口时显示纯文本提示。

### P2：文档与运行说明

- 补充应用、管道的运行和检查说明，明确增强库是来源线索而非完整 JD。
- 将本地数据快照、外部定时任务注册状态和数据来源条款核实列为带日期/责任人的待办；项目副本本身不能证明外部调度仍在运行或条款已获确认。
- 不把本地缓存、工作簿、增强库或个人数据加入新文档或公开提交。

## 验收条件

1. 三个页面均通过共享岗位库读取内置及可选增强库，历史意向不会因岗位不在当前库中而消失。
2. 增强岗位匹配结果标出覆盖率和资料有限状态，不将职位清单当成职责或完整 JD，不生成技能缺口。
3. 生成器只在来源事实存在时使用量化、成效、影响和协作关系；缺少事实时不编造填充词。
4. 合成工作簿测试证明职位拆分、方向推断、公司类型保留、稳定 ID 和可配置路径正确。
5. 现有经历挖掘测试与新加的岗位库、评分和数据转换定向测试通过。整个过程不访问外网、不改写用户源工作簿或现有增强 JSON。

## 尚不纳入实现

- 用生成式模型补齐完整 JD 或推测职位职责。
- 评估或宣称数据来源的法律授权状态。
- 运行或配置外部定时抓取服务。
- 重构画像、浏览器扩展、申请追踪和简历模板。
